## Product
Internal (not SaaS) fleet platform, one SA company, 50–200 vehicles, multi-branch, multi-shift (incl. across midnight), TZ Africa/Johannesburg. Mobile-first driver portal (mid-range phones, weak signal), desktop management app.

## Stack
Next.js App Router · React · TypeScript strict · Tailwind · shadcn/ui · Supabase Postgres/Auth/private Storage · Vitest · Playwright · GitHub Actions. Hosting (DEC-25/AD-09): self-hosted Supabase + Next.js on RSAWEB servers in South Africa, prod at fleetiq.outview.co.za. All data stays in South Africa; no foreign providers without approval. Modular monolith: `src/modules/<module>/{domain,services,data,ui}`, `src/lib`, `src/jobs`, `supabase/migrations`, `supabase/tests` (ARCH §3).

## Approved decisions (only these are fixed rules)
- DEC-08: drivers sign in with employee number + PIN; one company phone per driver.
- DEC-24: segregation of duties, no override — nobody approves/verifies/corrects their own record; supervisor can't approve on an allocation where they are the driver; service record verifier ≠ creator; no self-granted roles.
- DEC-32: "Operations manager" = Branch manager.
- DEC-34: office/management users sign in with email + password; MFA required for administrators and anyone with approval permissions.
- DEC-23: permission matrix = PRD §4.2 table, seeded as config. Key points: corrections approved by fleet admin (all) or branch manager (own branch); supervisors approve standard exceptions in own branch; senior management view-only; system admin manages users/settings and sees the audit log but has no access to evidence, reports or licence data.
- DEC-37: driver-register visibility (Approved 2026-11-17): supervisor, fleet admin, branch manager, senior management within scope; driver own record; maintenance and system admin none. Recorded on `driver_register_visible()`.
- DEC-19: service config precedence vehicle → make/model → category → company default (effective-dated, audited).
- DEC-20: go-live baselines need an invoice/job card/service-book photo, verified by the maintenance admin (verifier ≠ creator); none = baseline_required.
- DEC-31: branch transfers approved by a fleet admin; branch history kept.
- DEC-39 (Approved 2026-11-18): 3B allocation creation rules stand (planned times inside the shift window; vehicle, driver, shift in one branch; only available vehicles; no branch transfer / driver deactivation with live allocations).
- DEC-40 (Approved 2026-11-18): an allocation is started (planned → pre_inspection_pending) by its own driver, or by an `allocation.manage` holder for the branch on the driver's behalf with a reason; on-behalf starts are permanently flagged ("Started by supervisor"). Start window planned start − 60 min to planned end; licence re-checked at start; no-show from planned start + 30 min; 60/30 are configurable defaults (`allocation_settings()`).
- AD-01: background jobs = Postgres `background_jobs` table + scheduled worker (pg_cron trigger + Node worker on the server).
- AD-05: `user_roles` (branch_id nullable = company-wide) is the only branch-scope source.
- DEC-12/14/16/17/18 (configurable defaults in `odometer_validation_settings`): whole km; OCR–driver tolerance 0 km; unaccounted tolerance 5 km; late pre-shift +30 min, post-shift +60 min; stale after 7 days. DEC-13 (OCR confidence) and DEC-15 (max km/allocation) have no default: while unset, no auto-acceptance and the implausible check reports `not_configured`. DEC-44 (Approved 2026-11-25): acceptance before OCR is live (see Phase 5A below).
Everything else in PRD §12 / ARCH §17 is Proposed/Open → configurable, cite the ID.

## Roadmap (PRD §9)
0 Setup → 1 Foundation (auth, org/branches, roles/permissions, RLS, audit triggers, private evidence storage) → 2 Registers → 3 Shifts & allocations → 4 Inspections (mobile) → 5 Odometer manual path → 6 OCR → 7 Mileage → 8 Service monitoring & alerts → 9 Incidents, dashboard, reports → 10 Pilot. Never build ahead of the current phase.

## Non-negotiable rules
- Authorisation on the server AND in RLS; UI is never the security boundary. One helper `has_permission(key, branch_id)` for RLS and services.
- Service-role key: background jobs and reviewed admin functions only; never in user requests or the browser.
- Every schema change is a migration. text + CHECK statuses (catalogue DB §20). UUID PKs, timestamptz, integer km.
- No hard deletes of evidence/history; void or supersede. Accepted readings, evidence files, used template versions and audit rows are immutable. Audit via DB triggers.
- Idempotent submissions (`client_submission_id`) and jobs (`idempotency_key`).
- Loading/empty/error/success states; negative + permission tests; never claim untested work is done; no fake data.

## Odometer (PRD §5.8–5.9, ARCH §6.5, §7)
- Pre- and post-shift inspection per allocation, each with a mandatory odometer photo (in-app camera preferred; gallery/file flagged per DEC-04). No-photo path only via approved, permanently labelled exception (DEC-03).
- Three separate values, never one editable field: OCR reading · driver reading · accepted reading.
- Upload → server verify (type, size, SHA-256, strip EXIF GPS) → register `evidence_files`.
- Auto-accept only if: in-app capture AND OCR ≥ threshold AND driver = OCR within tolerance AND all checks pass. Else exception → review.
- Checks: decreasing, implausible distance, unaccounted distance vs previous allocation, OCR low/failed/mismatch, duplicate hash, gallery source, late, rollover/replacement, missing.
- Corrections create a superseding reading (approved by someone else) and trigger recalculation. Odometer replacement/rollover → approved adjustment → new segment; lifetime_km = displayed + offset.
- Distance = accepted post − accepted pre. Unaccounted = this pre − previous allocation's post. Missing/non-accepted → provisional/incomplete, never estimated. Never auto-attributed to a driver.
- "Latest accepted reading" = by allocation chronology (start time, then post after pre), not highest value or device time.
- OCR/AI is assistive only; manual path must work without it; AI never decides liability.

## Service monitoring (PRD §5.10, ARCH §8)
Default 15,000 km interval, ±1,500 km tolerance. next = last VERIFIED service odometer + interval (never rounded). Bands: <13,500 normal · 13,500–14,999 approaching · 15,000–16,500 due · >16,500 overdue · no verified record = baseline_required. Optional time basis; effective status = more severe of km and time. Only a verified service record (verifier ≠ creator) sets the baseline; never invent one. Config precedence (DEC-19, approved): vehicle → make/model → category → company default.

## Allocation lifecycle (PRD §5.5)
planned → pre_inspection_pending → in_use → post_inspection_pending → closed | closed_with_exceptions; plus cancelled, no_show. Transitions (enforced in the DB by `allocation_transition_allowed()` + `transition_allocation()`): planned→pre_inspection_pending|cancelled; pre_inspection_pending→in_use|no_show|cancelled; in_use→post_inspection_pending; post_inspection_pending→closed|closed_with_exceptions; closed_with_exceptions→closed; closed/cancelled/no_show terminal. `in_use` (set only by submitting the pre-shift inspection, `started_at` = its server submit time) and `post_inspection_pending` (set only by beginning the post-shift inspection) are enabled since 4A for those two paths only; every other caller still gets 0A000; closing stays a stub until Phase 5 (`released_at`, `closed_by` closed). No overlapping active allocations per vehicle (DB exclusion constraint). One non-void inspection per allocation + stage.

## Inspections (Phase 4A)
Templates are versioned config (`inspection_templates`/`_items`; immutable once `first_used_at` is set; one active per company+category; `inspection_template_for(vehicle)`); starter checklist v1 = DEC-21 (20 pre + 7 post items, fixture `starter-checklist.fixture.json`). One live inspection per allocation + stage; functions only (no client writes), each idempotent on `client_submission_id` (ledger `inspection_requests`, DEC-06) and carrying device time + `captured_offline`. Odometer/condition photos must be `in_app_camera` (DEC-04), uploaded by the person completing the inspection, same branch; retakes keep both. Submit needs: vehicle confirmed, every required item, Defect = comment + item photo, Yes = comment, current odometer photo (no bypass until Phase 5). Late (DEC-17 as amended 2026-11-24) = server submit time more than 30 min after the ALLOCATION's planned start (pre) / 60 min after its planned end (post); never blocks. Void: `allocation.manage`, reason, not the completer (DEC-24), does not move the allocation. Supervisor on-behalf (DEC-09) and the damage register are 4C (below).

## Camera, photos, devices (Phase 4B)
- In-app camera only (DEC-04/41): no file picker/gallery anywhere in the inspection flow; JPEG ~1600 px long edge, quality 0.85 (`CAMERA_CAPTURE` in evidence-config). Steps: confirm vehicle → checklist → defect photos → odometer photo → review → Submit; each photo = request slot → upload → register → attach, each step with its own `client_submission_id`, retried with the same ids. `submitBlockers()` mirrors submit_inspection (IN001–IN006); the server stays the final word.
- `evidence_files`/slots carry restricted `capture_latitude/longitude/accuracy_m` (DEC-29): NO role can SELECT them through the table (column grants); `evidence_capture_location()` = `odometer.exception.review` holders for the branch, never the uploader, logged as `location_viewed`. Also `captured_offline` and `device_id`. Audit rows never receive the location.
- Company device register (DEC-35): `company_devices`, managed with `driver.manage` (not your own device, DEC-24). Phone's device key = random UUID in IndexedDB/localStorage, untrusted, flags only: `inspections.device_flag` = issued_device | other_device | unknown_device | no_issued_device, set in submit_inspection from the current odometer photo's device. Never blocks.
- First-use camera notice acknowledged per version (`camera_notice_acknowledgements`); declining never blocks.
- Post-shift: driver confirms before it begins (allocation moves to post_inspection_pending at once); after submit it stays there — closure and `released_at` are Phase 5. Offline queue and missing/late detection = 4D (below).

## Damage register and on-behalf (Phase 4C)
- DEC-42 (Approved 2026-11-24): zones (fixed list, `damage_zones()`/`damage_zone_label()`, mirrored in `damage-zones.ts`): front_bumper, bonnet, windscreen, roof, rear_bumper, rear_boot_load_area, left_front, left_rear, right_front, right_rear, wheels_tyres, interior, other. Severity minor|moderate|major; description 1–500 chars; at least one in-app-camera photo (DEC-04/41). Status: reported → verified | disputed; verified → repaired; disputed and repaired are final (correct by reporting a new item).
- Review: `allocation.manage` for the vehicle's branch verifies/disputes (dispute needs a reason); `service.record.create` marks repaired (note). Nobody reviews or repairs an item they reported (DEC-24, also CHECKs). Day-one "onboarding" items count as known at once, never raise the new-damage flag, still need a different reviewer. No new permission keys (DEC-23).
- Pre-shift report of damage not in the register ⇒ `inspections.new_damage_flag` and the item records the vehicle's previous used allocation (by chronology) and its submitted post-shift inspection. Post-shift reports never flag. Neither assigns fault; the UI never says so.
- The driver confirms "I have checked the known damage list" (`confirm_known_damage_reviewed`, IN007 at submit, after IN001). Drivers read the register only while holding a live allocation (pre_inspection_pending, in_use, post_inspection_pending); photos stay behind `can_view_evidence` (a driver sees the list, not other people's photos — default to confirm).
- DEC-09: `begin_inspection_on_behalf` — post-shift only, caller holds `inspection.submit` AND `allocation.manage`, is not the driver, reason 1–500; in_use → post_inspection_pending via transition rule e (on-behalf flag); a driver's existing draft must be voided first. `completed_by_role = 'supervisor_on_behalf'` + `on_behalf_reason` permanent; the completer check (`inspection_load_for_driver`) is one function for every write; the completer cannot void it (DEC-24). Device flag is stored against the DRIVER's phone and shown neutrally ("Completed by supervisor on their own phone"). Closure and exceptions stay Phase 5; offline queue and missing/late detection are 4D (below); incidents Phase 9.

## Offline and detection (Phase 4D)
- DEC-06/DEC-43 (Approved): ONE write path — every inspection write (begin, save answers, confirm known damage, photo slot→upload→register→attach, report damage, submit) is saved on the phone first and sent in order by the queue, online or offline (`begin` for a driver; on-behalf `begin` stays online-only). Each item has its own `client_submission_id`, made when the driver acts and reused on every retry; a replay answer = success; device time untrusted; `captured_offline` = the phone was offline when the driver acted. Starting an allocation needs a connection (DEC-40): offline the card says "Starting needs a connection".
- Phone storage (IndexedDB `fleetiq-offline`, every record keyed by profile id, no read across profiles): `items` (ordered queue), `blobs` (the ~1600 px JPEGs until attach/report is confirmed), `scopes` (per-inspection conflict state), `refs` (scope → server inspection id once `begin` is confirmed), `snapshots` (24-hour snapshot + "last updated"). Code: `src/modules/inspections-damage/offline/{domain,server,ui}`; the form shows the server's data (live page or snapshot) with the unsent queue applied (`applyQueue`). Sign-out with unsent items is allowed after a warning; the items stay and send after that driver's next sign-in (another driver never sees or sends them; the server also refuses a queue under another session: 401 WRONG_USER).
- Errors (`classify.ts`, one place): network/timeout/408/425/429/5xx = retry (exponential backoff 2 s → 5 min, same csid); 401 = pause until sign-in; any other server answer (403/404/409/410/422, SQLSTATE/IN0xx/DM0xx/EV0xx, "already used for a different request") = CONFLICT: that inspection's queue stops, nothing is dropped, the server's message is shown as is and reported (`report_sync_conflict`, refusal only — no photos/answers). A supervisor with `allocation.manage` (not the reporter, DEC-24) resolves it with a note; only then can the driver "Remove from this phone" (what goes is listed first; nothing on the server is touched). Upload slots (15 min) are requested right before the upload and re-requested with the same csid when one expires. "Still not sent after 30 min" warning: `OFFLINE_CONFIG.stuckAfterMinutes`.
- Service worker (`public/sw.js`): caches ONLY `/_next/static/*`, the `/offline` shell and the icon; NEVER `/api/*`, non-GET, cross-origin (signed photo URLs), RSC payloads or any page HTML. A driver page that cannot be reached is answered with a redirect to `/offline?next=…`, a static page that draws the allocations/forms from IndexedDB.
- Detection: `inspection_due_status()` (SQL, mirrored in `inspection-due-status.ts` + shared fixture): pre-shift overdue = no submitted pre-shift inspection after planned start + `pre_shift_late_minutes` (30) while planned/pre_inspection_pending; post-shift after planned end + 60 while in_use/post_inspection_pending; strict; cancelled/no_show = not_applicable. `list_overdue_inspections()` is live (every read; allocation.manage / reports.view per branch; no driver names, DEC-41) and also lists open sync conflicts; page `/shifts/missing` + badge in the Shifts nav. `inspection_watch_findings` records each overdue inspection ONCE (UNIQUE allocation+stage+finding) via `run_inspection_watch()` (service_role only, idempotent, resolves on submit/cancel/no-show). No exceptions and no notifications in 4D (Phase 5 exceptions, Phase 8 alerts read the findings).
- Job schedule (RSAWEB, AD-01; pg_cron is NOT in migrations): every 5 minutes run `npm run job:inspection-watch` (enqueues `inspection_watch:<company>:<5-minute bucket>` per company and runs it) from the host's cron, or have pg_cron enqueue with the same key and let the Node worker drain: `select public.enqueue_background_job('inspection_watch', 'inspection_watch:' || c.id || ':' || to_char(date_trunc('hour', now()) + floor(extract(minute from now()) / 5) * interval '5 minutes', 'YYYY-MM-DD"T"HH24:MI'), '{}', c.id) from public.companies c;` Evidence cleanup stays hourly (`npm run job:evidence-cleanup`).

## Odometer manual path, part 1 (Phase 5A)
- Settings (`odometer_validation_settings`, migration 051): effective-dated versions per (company, category; null = company default), seeded 0 / 5 / 30 / 60 / 7 km·min·days with `max_km_per_allocation` and `ocr_min_confidence` NULL (DEC-13 / DEC-15). `validation_settings_for(vehicle, at)` = category row, else company default (ONE place). `allocation_settings()` takes the late minutes from the company-default row now in effect. Change only through `set_validation_settings` (`settings.validation.manage`, company-wide grant, reason, closes the old version, audited); page `/settings/validation`. Segments (`odometer_segments`): one open per vehicle (segment 1, offset 0, backfilled); `lifetime_km = displayed + offset` in `odometer_lifetime_km()`.
- Driver entry (DEC-05 blind): after the odometer photo the driver types whole km (0–9,999,999, digits only) — `record_driver_reading` (completer only, draft only, needs the current photo, idempotent on `inspection_requests`, own csid; a retake re-links the reading). Queue item kind `reading`, op `record_reading` on `/api/inspection-sync`, same order/retry/conflict rules as 4D. `submit_inspection` refuses without it (IN015) and, in the same transaction, runs `odometer_validate` and moves the reading to `awaiting_review`. No OCR column is ever granted or sent (`odr_ocr_not_yet` CHECK keeps `ocr_*` NULL until Phase 6). The driver sees only their typed value and "Reading sent for checking" / "Accepted" / "Needs a supervisor".
- Validation (`odometer_evaluate_checks`, pure; TS mirror `odometer-mileage/domain/validation.ts`, same vectors): decreasing (vs latest ACCEPTED reading before it by allocation chronology: planned start, then pre before post — never by value), implausible distance (post, `not_configured` while max is null), unaccounted distance (pre; waiting while the previous post-shift reading is unaccepted), duplicate image (sha256), gallery (recorded, cannot fail: DEC-04), late. Results: pass | fail | not_configured | waiting; only `fail` counts. Each failed check = one open `odometer_exceptions` row (high: decreasing/duplicate; medium: unaccounted/implausible; low: late). Re-validation of the vehicle's LATER awaiting readings runs when a reading is accepted or rejected; a move between queues is a recorded `validated` event.
- DEC-44 (Approved 2026-11-25): no auto-acceptance before OCR (`odometer_auto_accept_allowed()` = false, tested). No failed check → quick photo check (`odometer.exception.review`: `quick_check_accept`, per-item results, stale item refused via `validated_at`; "doesn't match the photo" = `send_to_full_review` with a note + an `other` exception). A failed check, or sent from the quick check → full review (`odometer.exception.approve`: `review_reading` accept | accept_value | reject, reason required, the driver value is never edited; one `approvals` row of type `odometer_exception` with `requested_by` = the reading's submitter so `approvals_no_self_decision` stays meaningful; the exceptions are resolved/dismissed with its id). Nobody checks or decides a reading they entered, one from an inspection they completed, or one on an allocation they drive (OD006; CHECKs on the reading too). Error codes OD001–OD011 (`odometer_messages()`, mirrored in `odometer-errors.ts`).
- Reads/RLS: no client writes. Readings: the allocation's driver (column grant without reviewer fields) and `odometer_can_read` (review holders, or `reports.view` holders who may see the driver register — maintenance and system administrators see nothing). Reviewer lists/detail/counts are SQL functions (`list_odometer_review`, `odometer_review_detail`, `odometer_review_counts`); driver names only when `driver_register_visible()` (DEC-41). Photo through the existing signed-URL path (logged). UI `/odometer/review` (quick check, full review, detail), counts beside the Missing / Late list. Accepted readings are immutable (accepted → superseded is 5B); the vehicle cache follows allocation chronology. Corrections/adjustments/replacement inspections 5B; no-photo exception, missing/late exceptions, closure 5C.

## Privacy (POPIA)
Minimise personal data; restricted licence data; private evidence with short-lived signed URLs, every access logged; no invented retention periods (DEC-27).
